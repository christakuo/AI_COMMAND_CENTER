# AI_COMMAND_CENTER 使用 SOP

## 1. 專案定位

AI_COMMAND_CENTER 是元馨健康生活事業的 **AI 工作指揮中心**。

本專案集中管理：

- 公司與品牌背景資料
- AI 工作技能規則（Skills）
- 標準作業流程（SOP）
- 事業發展藍圖（roadmap）
- 實際產出成果（outputs）

Codex 會依照專案內的背景資料與工作規則，協助執行下列任務：

- 健康管理
- 健檢報告分析
- 健康風險整理
- 健康管理會員分級
- LINE 會員經營與推播
- 長照資源整合
- 企業健檢提案
- 企業 ESG 健康管理
- 醫療與照護資源轉介流程規劃

使用本專案的核心原則是：

> 先讀取正確資料，再依照 Skill 執行，確認內容後才建立正式成果。

## 2. 資料夾用途說明

| 資料夾 | 用途 | 何時使用 |
|---|---|---|
| `company/` | 公司、品牌與業務背景資料 | Codex 需要理解公司、品牌、服務內容時 |
| `skills/` | AI 工作技能規則 | Codex 執行特定任務前需讀取 |
| `sop/` | 標準作業流程 | 操作 GitHub、Codex、專案管理或執行固定流程時使用 |
| `roadmap/` | 事業發展藍圖 | 規劃未來產品、平台、年度目標與服務時使用 |
| `outputs/` | 實際產出成果 | 保存提案、範本、流程驗證結果與正式報告範本 |

### 資料夾使用原則

1. `company/` 放長期有效的公司知識，不放單次客戶報告。
2. `skills/` 放 Codex 執行任務時必須遵守的規則。
3. `sop/` 放人員操作及專案管理流程。
4. `roadmap/` 放未來發展、年度計畫與執行順序。
5. `outputs/` 放已完成、可重複參考或可交付的成果。

5. 醫療、保險與長照相關 Skill 必須保留安全及合規聲明。

## 5. 每次使用 Codex 的標準流程

### 開始任務前

| 步驟 | 操作 | 確認重點 |
|---|---|---|
| 1 | 打開 GitHub Desktop | 確認程式已正常開啟 |
| 2 | 確認 Current repository | 必須是 `AI_COMMAND_CENTER` |
| 3 | 確認 Current branch | 應為 `main` |
| 4 | 點選 Fetch origin | 檢查 GitHub 是否有新版本 |
| 5 | 如出現 Pull origin，先執行 Pull | 先取得最新內容，避免版本衝突 |
| 6 | 確認 No local changes | 確認沒有尚未處理的修改 |
| 7 | 開始使用 Codex | 清楚說明本次任務與限制 |

> 如果 GitHub Desktop 顯示不明修改，先確認修改來源，不要直接覆蓋或刪除。

### 使用 Codex 時

1. 明確指定要先讀取哪些文件。
2. 明確指定要修改或新增哪一個檔案。
3. 若只是驗證流程，請說明「先不要修改檔案」。
4. 若要建立新檔案，請提供完整路徑與檔名。
5. 明確列出不可修改的資料夾或文件。
6. 每次盡量只修改一個檔案，降低錯誤風險。
7. 要求 Codex 完成後回報新增或修改的檔案。
8. 重要內容可先產出草稿，確認後再寫入正式檔案。

### Codex 完成後

| 步驟 | 操作 | 確認重點 |
|---|---|---|
| 1 | 檢查 Codex 產出的內容 | 確認資料、表格、語氣及合規聲明 |
| 2 | 到 GitHub Desktop 查看 Changes | 查看實際新增或修改內容 |
| 3 | 確認只修改預期檔案 | 不應出現無關檔案 |
| 4 | 填寫 Summary | 使用清楚、可辨識的中文說明 |
| 5 | 點選 Commit to main | 將本次修改建立版本紀錄 |
| 6 | 點選 Push origin | 將版本同步至 GitHub |
| 7 | 回 GitHub 網頁版確認 | 確認檔案與最新 Commit 已成功同步 |

### 標準流程圖

```text
確認 GitHub Desktop
        ↓
取得 GitHub 最新版本
        ↓
確認沒有未處理修改
        ↓
向 Codex 說明讀取文件與任務
        ↓
Codex 執行並回報修改檔案
        ↓
人工檢查內容與 Changes
        ↓
Commit to main
        ↓
Push origin
        ↓
GitHub 網頁確認
```

## 6. 什麼情況開新對話

| 情況 | 建議方式 | 原因 |
|---|---|---|
| 同一個任務尚未完成 | 繼續同一個 Codex 對話 | Codex 可保留前面的任務背景與決策 |
| 同一份文件需要接續修正 | 繼續同一個 Codex 對話 | 可避免重複說明 |
| 改用不同 Skill | 建議開新對話 | 避免不同工作規則互相混淆 |
| 改做不同模組 | 開新對話 | 讓任務範圍更清楚 |
| 改做不同業務 | 開新對話 | 例如企業健檢與長照服務應分開 |
| 舊任務已完成，開始新目標 | 開新對話 | 方便日後搜尋與管理紀錄 |

### 專案歸屬原則

- 與元馨醫管家、AI馨健康、企業健檢、ESG健康促進、會員管理、LINE推播及長照整合有關的工作，放在 `AI_COMMAND_CENTER` 專案下。
- 與本專案無關的獨立系統或其他公司專案，應使用各自的專案資料夾與對話。

## 8. 命名規則

### Skill 檔案命名

建議格式：

```text
skills/任務名稱.md
```

範例：

```text
skills/健康管理會員分級.md
skills/長照資源整合提案.md
skills/保險顧問健康轉介.md
```

命名原則：

- 使用清楚的中文任務名稱。
- 檔名應直接說明 Skill 用途。
- 避免使用「新版」、「最新」、「最後版本」等不易管理的字樣。

### outputs 檔案命名

建議格式：

```text
outputs/狀態_主題_流程或用途.md
```

範例：

```text
outputs/正式版會員健檢分析_分級_LINE推播範本.md
outputs/正式版會員分級_長照需求判斷_LINE推播範本.md
outputs/300人科技公司企業健檢_ESG健康促進提案大綱.md
```

命名原則：

- 可使用「草稿」、「確認版」、「正式版」表示文件狀態。
- 將主要流程以底線 `_` 分隔。
- 個案資料若含個資，檔名避免直接使用完整姓名或身分證字號。

### Commit 訊息命名

建議格式：

```text
新增：文件或功能名稱
更新：文件或規則名稱
修正：問題或內容名稱
```

範例：

```text
新增：AI_COMMAND_CENTER 使用 SOP
新增：長照需求與 LINE 推播正式範本
更新：Skills 中心使用說明
修正：會員分級範本表格內容
```

### Codex 對話命名

建議格式：

```text
[業務模組] 任務名稱
```

範例：

```text
[健檢分析] 建立個人報告分析範本
[會員管理] 會員分級與LINE推播流程
[長照整合] 長照需求判斷流程
[企業ESG] 300人科技公司提案
[專案管理] AI_COMMAND_CENTER使用SOP
```

## 9. 安全與合規提醒

### 健康與醫療

- 健康分析不可取代醫師診斷。
- 不可直接診斷疾病。
- 不可宣稱可以治療疾病。
- 不可保證健康改善結果。
- 資料不足時應明確列出，不可自行推測。
- 若出現明顯危險訊號，應提醒儘速就醫。

### 保險

- 保險內容不可構成特定商品推薦、招攬或投保建議。
- 不可保證投保、承保或理賠結果。
- 不可推薦特定保費或保額。
- 如需轉介保險顧問，應先取得會員同意。

### 長照

- 長照內容不可判定政府長照資格或失能等級。
- 不可保證取得政府補助、服務名額或特定資源。
- 不可保證媒合特定機構、看護或照護人力。
- 應由醫師、社工師、照管專員或相關政府單位進行正式評估。

### 個資與轉介

- 轉介前需取得會員或家屬同意。
- 應清楚說明轉介目的與資料使用範圍。
- 不可將健康資料提供給未經同意的第三方。
- outputs 如含個人資料，應限制使用範圍並避免公開。
- 提供企業報告時，應避免揭露可識別個人的健康資訊。
