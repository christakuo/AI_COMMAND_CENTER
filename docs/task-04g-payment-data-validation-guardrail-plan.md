# Task 04G：正式 leads 付款資料驗證與人工防呆規劃

## 1. 任務目的

本任務規劃正式 `leads_潛在會員名單` 中付款完成、成交及顧問歸屬相關欄位的資料驗證與人工警示方式，以降低人工維護錯誤，避免顧問獎金系統將不完整、測試、官方歸屬或有爭議的名單誤判為可發獎金名單。

本階段只完成文件化規劃，不會在正式 Sheet 套用設定，也不會修改任何程式或產生獎金草稿。

## 3. 需要防呆的欄位

| 欄位名稱 | 建議資料驗證 | 允許值或格式 | 錯誤範例 | 錯誤風險 |
|---|---|---|---|---|
| 是否已付款 | 下拉選單 | `是`、`否` | 已付款、YES、Y、包含空格的「是」 | 系統無法正確辨識付款資格 |
| 付款完成時間 | 有效日期時間驗證；統一顯示格式 | `yyyy-MM-dd HH:mm:ss` | 簽約時間、預計付款時間、任意文字 | 成交日期錯誤或名單被錯誤排除／納入 |
| CRM 階段 | 使用既有正式階段下拉選單 | 依正式用語，例如「付款完成」或「已成交（付款完成）」 | 實際未付款卻填付款完成 | 人工誤認為已符合獎金資格 |
| CRM 階段更新時間 | 有效日期時間驗證 | `yyyy-MM-dd HH:mm:ss` | 任意文字、填入付款完成時間欄 | 被誤當作實際付款完成時間 |
| 歸屬顧問 ID | 格式檢查並與正式顧問清單核對 | `HC` 加四位數字，例如 `HC9999` | HC999、9999、直接填顧問姓名 | 獎金錯發、漏發或歸屬錯誤 |
| 歸屬顧問姓名 | 與正式顧問清單及顧問 ID 交叉核對 | 必須與顧問 ID 對應 | `HC9999` 對應到其他顧問姓名 | 人工審核誤判顧問歸屬 |
| 推薦碼 | 格式檢查並核對推薦來源 | 有效推薦碼，例如 `HC9999` | 無效代碼、人工臆測補填 | 推薦來源、保護期或顧問歸屬錯誤 |
| 是否測試資料 | 下拉選單 | `是`、`否` | test、Y、空格 | 測試資料混入正式獎金流程 |
| 爭議狀態 | 下拉選單 | 建議：無爭議、待審核、已確認、已駁回 | 處理中、任意備註、未統一用語 | 未解決爭議進入獎金草稿 |
| 名單 ID | 必填、格式及重複檢查 | 依正式 ID 格式；每筆唯一 | 空白、重複 ID、以會員姓名代替 | 防重失效、資料連結或獎金歸屬錯誤 |

正式設定前，必須先盤點目前 Sheet 已使用的 CRM 階段與爭議狀態文字，再決定正式下拉選項，避免同一狀態出現多種近似用語。

## 4. 「是否已付款」欄位規劃

- 建議設定下拉選單，只允許「是」或「否」。
- 未來新資料建議預設為「否」，避免無法區分「未付款」與「尚未維護」。
- 既有空白資料第一階段先保留，不要直接大量改寫成「否」。
- 既有空白可能代表未付款、歷史資料不完整或尚未確認，應先人工盤點再分批處理。
- 只有「是否已付款＝是」且付款完成時間為有效日期時間，才可能符合獎金資格。
- 下拉選單只限制未來輸入方式，不能取代付款事實核對。

## 5. 「付款完成時間」欄位規劃

- 統一顯示格式為 `yyyy-MM-dd HH:mm:ss`。
- 建議設定有效日期時間驗證，避免輸入一般文字。
- 建議加入欄位說明：

  > 只填實際收款完成時間；不要填簽約時間、CRM 階段更新時間或預計付款時間。

- 建議使用條件格式標示「是否已付款＝是，但付款完成時間空白」的資料列。
- 不應只看畫面顯示是否像日期，也要確認儲存內容確實是日期時間值，而不是文字。
- 若付款後發生退款、刷退或取消，不應只刪除時間掩蓋歷史，應先進入爭議或停止處理流程。

## 6. 顧問 ID 防呆規劃

- 歸屬顧問 ID 建議格式為 `HC` 加四位數字，例如 `HC9999`。
- 格式正確不代表顧問一定存在，仍須與正式顧問清單核對。
- `HC0000` 應標示為官方來源，不可發會員推薦獎金。
- 「是否已付款＝是，但歸屬顧問 ID 空白」時，應標紅並停止進入獎金流程。
- 顧問 ID 與顧問姓名不一致時，必須人工核對，不得自行選一個欄位作準。
- 推薦碼與歸屬顧問 ID 不一致時，不可直接判斷為錯誤，也不可自動覆寫。
- 不一致時應查閱推薦事件、保護到期日及爭議狀態，再由顧問管理負責人確認正式歸屬。

## 7. 測試資料與爭議狀態

### 是否測試資料

- 建議設定下拉選單，只允許「是」或「否」。
- 未來新正式名單可預設為「否」；既有空白仍須先盤點。
- 「是否測試資料＝是」的名單不得進入正式獎金草稿。
- 即使付款及顧問欄位完整，測試資料仍不得放行。

### 爭議狀態

- 建議至少統一為：無爭議、待審核、已確認、已駁回。
- 「爭議狀態＝待審核」時，應以條件格式標示並暫停進入獎金流程。
- 顧問歸屬、推薦來源、保護期或付款狀態尚有爭議時，不得改成可發獎金狀態。
- 現階段先以 Task 04F SOP 與人工核對控制；未來有需要時，再補 Apps Script 阻擋規則。

## 8. 最小條件格式建議

為避免正式 Sheet 顏色過多、難以判讀，第一階段只建議設定以下五項：

| 優先順序 | 條件 | 顯示方式 | 操作意義 |
|---:|---|---|---|
| 1 | 是否已付款＝是，但付款完成時間空白 | 標紅 | 必須補正，禁止進入獎金流程 |
| 2 | 是否已付款＝是，但歸屬顧問 ID 空白 | 標紅 | 必須先確認顧問歸屬 |
| 3 | 是否已付款＝是，且歸屬顧問 ID＝`HC0000` | 標黃 | 官方來源，不發會員推薦獎金 |
| 4 | 是否測試資料＝是 | 標灰 | 測試資料，不得進入正式流程 |
| 5 | 爭議狀態＝待審核 | 標橘 | 暫停處理，等待人工確認 |

### 設定原則

- 條件格式只是視覺警示，不是自動修正資料。
- 條件格式不可取代正式 Preview 與人工逐筆核對。
- 實作前必須先確認正式 Sheet 每個欄位的實際欄位字母與資料範圍。
- 在欄位字母尚未確認前，不應直接套用固定公式，以免警示引用錯欄。
- 後續應先用少量測試列驗證規則，再套用到正式資料範圍。

## 9. 是否需要修改 Apps Script

現階段暫時不需要修改 Apps Script，可先用以下方式控制風險：

- Google Sheet 下拉選單。
- 有效日期時間驗證。
- 最小條件格式。
- Task 04F 人工維護 SOP。
- 正式 Preview。
- 人工逐筆核對。

未來若付款資料量增加、相同錯誤重複發生，或人工核對已難以負荷，再規劃 Apps Script 唯讀檢查工具。未來工具可考慮檢查：

- 付款欄位是否完整且格式正確。
- 顧問 ID 是否存在於正式顧問清單。
- 顧問 ID 與顧問姓名是否一致。
- 名單 ID 是否重複。
- 爭議狀態是否阻擋獎金流程。
- 異常資料清單及原因摘要。

若新增工具，第一版應只產生唯讀檢查報告，不應自動修改正式資料。
