## 1. 任務目的

本任務是「元馨醫管家顧問獎金系統」全面上線總盤點，不是針對單一顧問、單一獎項或單一月份修補。目標是一次確認：

1. 新顧問如何由線上合約自動進入顧問主檔。
2. 新會員如何自動進入會員、`leads` 與成交資料。
3. 顧問與會員線上合約如何串接主資料庫。
4. Gemini 建立的業績獎金表是否仍為正式流程的一部分。
5. 顧問的上線、指定導師、位階與多層組織關係如何建立及保留歷史。
6. 顧問首次登入時如何安全地自動綁定 LINE UID，及後續如何受控改綁。
7. B01～B08 各獎項的資料、計算、Preview、Generate、防重、覆核、顯示及驗收完整度。
8. 哪些步驟可自動完成，哪些決策必須由人工覆核。
9. 顧問大廳應顯示哪些推薦、團隊、獎金、合約與權限資料。
10. 完整正式上線仍缺少哪些核心模組、控制與營運 SOP。

本任務執行邊界如下：

- 本任務未修改程式。
- 本任務未修改正式 Sheet。
- 本任務未部署。
- 本任務未執行 Apps Script。
- 本任務未執行 Preview 或 Generate。
- 本任務未進入 04H-2N。

## 2. 使用者核心要求

本系統必須以可持續擴充的公司流程設計，不得以目前個案數量作為系統邊界：

- 不只處理蕭志正；導師獎金與團隊查詢必須適用所有現在及未來符合資格的導師。
- 不只處理目前 13 位顧問；新加入、晉升、停權、離開及組織異動都要進入一致流程。
- 不只處理目前 2 筆 B01 獎金；完整上線範圍是 B01～B08。
- 未來新顧問與新會員要由合約、付款及主檔流程自動串接。
- 獎金候選、規則計算與防重應自動化；人工負責例外判定、覆核、核准及撥款確認，不應人工試算或假造資料。
- 顧問大廳至少要能安全查詢自己的獎金與授權範圍內的團隊會員。
- Gemini 業績獎金表、顧問／會員線上合約、公司收到合約副本的流程，必須納入正式資料流與 source of truth 盤點。

## 5. 正式目標資料流

### 5.1 新顧問流程

顧問招募／線上合約完成  
→ 驗證合約完整性、唯一識別及同意版本  
→ 自動建立或受控更新 `consultants_顧問主檔`  
→ 產生穩定且不可重用的 `consultantId`  
→ 產生唯一 `referralCode`  
→ 依核准事件建立上線、指定導師、位階與組織路徑  
→ 發送顧問大廳連結  
→ 顧問首次 LIFF 登入  
→ 由後端驗證可信任 LINE 身分與顧問本人資料  
→ 自動綁定 LINE UID；衝突則停止並進人工覆核  
→ 顧問只可查自己的推薦名單、授權團隊會員與獎金。

自動化範圍：合約接收、去重、ID／推薦碼建立、通知、首次綁定候選。  
人工覆核範圍：重複身份、導師／組織歸屬例外、LINE 衝突與改綁。

### 5.2 新會員流程

會員線上合約完成／付款完成  
→ 以穩定識別建立或更新 `leads`／member record  
→ 驗證推薦碼、推薦保護與顧問歸屬  
→ 合約、付款、方案三項成交條件成立  
→ 建立不可變成交與歸屬快照  
→ 進入 bonus candidate  
→ 進入 Preview  
→ 人工覆核例外與計算結果  
→ Generate 正式 `bonus_records`  
→ 顧問大廳 read-only 顯示。

自動化範圍：合約／付款事件接收、主檔合併、歸屬候選、成交快照、獎金候選。  
人工覆核範圍：推薦爭議、資料不完整、退款／取消、特殊核准。

### 5.3 獎金流程

成交資料或期間彙總條件  
→ bonus candidate  
→ 依成交當時快照與核准規則版本計算 B01～B08  
→ 唯讀 Preview result  
→ 人工覆核／退回修正  
→ 重新 Preview 並核對 fingerprint  
→ 經授權 Generate  
→ `bonus_records` 一獎項一受益人正式明細  
→ 顧問端 read-only 查詢  
→ 核准排款  
→ 撥款結果確認  
→ 必要時走調整／追回，不覆寫歷史。

### 5.4 必要控制點

- Preview 與 Generate 必須共用同一套計算與資格判定邏輯。
- Generate 前必須重新比對來源 fingerprint、規則版本與人工覆核識別。
- 組織與資格必須使用「成交當時快照」，不能以今日主檔倒推歷史獎金。
- 查詢身份由後端從可信任 LINE token 決定，不接受前端自行指定 consultantId。
- 合約寫入、主檔建立、通知寄送必須各自有成功／失敗狀態，不得互相代替。

| `bonus_records_獎金明細表` | 一獎項對一位受益人的正式獎金明細 | **是：正式獎金明細權威**；撥款歷史另由批次／attempt 記錄承載 | 已有 2 筆 B01 的最新現況待實證核對 |

| 會員線上合約 | 會員同意、方案與簽約完成事件 | **應是：會員合約完成證據**；付款須另有權威來源 | 寫入哪張 Sheet、如何合併 leads／member 待查 |
| 合約副本寄送流程 | 公司及簽署人取得副本 | **否：主資料 source of truth** | 寄信成功不可取代合約與主檔交易成功；需查失敗補送與稽核 |

### source of truth 決策原則

1. 顧問身份、會員身份、合約、付款、成交、組織／資格事件、獎金與撥款分別指定權威來源。
2. Gemini 表如為報表，只能讀取權威資料，不得反向成為第二套可編輯主檔。
3. 若現況存在雙寫，須先定義主寫入端、同步方向、唯一鍵、失敗補償與停用舊流程日期。
4. 在完成 SOURCE 盤點前，不可對正式資料重新 Generate。

### 顧問端資料顯示原則

- 只回傳完成該畫面所需的最小欄位。
- 不顯示完整 LINE UID、會員完整個資、銀行資料、內部 guardrail、runId、fingerprint 或規則內部參數。
- 導師停權、資格喪失或組織異動後，團隊會員權限須依生效時間立即更新。
- 前端只負責呈現；查詢對象與資料範圍由後端驗證身份後決定。

## 9. 風險與缺口

| 風險 | 可能影響 | 必要控制 |
|---|---|---|
| 單點修補 | 每新增顧問或獎項就需人工改程式，規則互相矛盾 | 先完成資料契約、事件模型與通用規則引擎，不寫個人特例 |
| Gemini 表與主資料庫不一致 | 同一顧問、成交或獎金出現兩個答案 | SOURCE 任務盤點欄位、寫入端、同步方向及停用方案 |
| 顧問主檔 source of truth 不明 | 重複 consultantId、錯誤導師及權限 | 指定顧問身份權威與組織／資格事件權威 |
| LINE UID 長期人工綁定 | 無法擴大、易綁錯人、難以稽核 | 首次登入安全驗證、自動候選、衝突阻擋及受控改綁 |
| 組織路徑使用 `indexOf` 模糊比對 | ID 子字串相似時誤納入團隊並誤發獎金／洩漏資料 | 使用結構化 parent／path token、穩定 ID、有效區間與精確比對 |
| B03～B08 未實作卻宣稱完成 | 漏發、錯發，造成顧問信任與財務爭議 | 依第 7 節逐項通過八個完整度欄位後才算完成 |
| 人工覆核流程不完整 | 無法退回、調整或追蹤誰核准 | 狀態機、角色分工、原因碼、不可變 audit、核准版本及關帳 |
| 顧問看到他人資料 | 個資與商業機密外洩 | 後端 token 身份、欄位白名單、授權路徑及負向越權測試 |
| 新顧問／新會員不能自動串接 | 人工積壓、漏建檔、漏算獎金 | 合約／付款事件化、唯一鍵、去重、重試、失敗佇列與對帳 |
| 舊文件與最新正式狀態不一致 | 團隊誤以舊紀錄做決策 | SOURCE 任務建立有日期、版本與證據連結的現況清冊 |
| 在資料源未釐清前重跑 Generate | 重複獎金或錯誤正式明細 | 維持禁止，直到 source of truth、月份、版本、fingerprint 均核准 |

## 11. 下一步具體任務建議

同意下一步優先執行：

**Task 04H-2M-4D-4G-SOURCE｜Gemini 業績獎金表、線上合約與主資料庫 source of truth 盤點**

理由：目前最大風險不是缺少某一段獎金公式，而是不確定顧問合約、會員合約、Gemini 表、`consultants`、`leads`、成交資料與 `bonus_records` 之間誰寫入誰、誰才是權威。若先做 B03 或 LINE 綁定，可能把新功能接到錯誤或重複資料源上，後續必須重做。

### SOURCE 任務建議拆成四個唯讀工作包

1. **前端合約入口盤點**：確認四個已知檔案的送出端點、payload、成功／失敗判定、重試及副本寄送。
2. **後端接收與寫入盤點**：由 Apps Script route 追到實際 Spreadsheet／工作表／欄位、唯一鍵與觸發器。
3. **正式 Sheet 唯讀盤點**：核對【業績與獎金結算後台】與 Gemini 業績獎金表的分頁、公式、資料量、最後更新、寫入者及重複範圍。
4. **權威資料決策**：產出現況資料流、目標資料流、重複資料源處理、遷移／停用方案及每一業務事實的 source of truth 表。

### SOURCE 任務停止條件

- 僅唯讀盤點，不修改前端、Apps Script 或正式 Sheet。
- 不執行 Preview／Generate。
- 遇到 Spreadsheet ID、憑證、token 或個資時，只記錄安全識別與欄位結構，不寫入文件。
- 找不到實證時標示「未知／待確認」，不得用推測補齊。

## 12. 不得做的事

- 不得只針對蕭志正寫特例。
- 不得只針對目前 13 位顧問寫死名單或邏輯。
- 不得只完成 B01 就宣稱完整獎金系統完成。
- 不得繞過線上合約資料流另建無法對帳的顧問或會員資料。
- 不得長期人工補 LINE UID；人工只可處理受控例外與改綁審核。
- 不得人工假造獎金資料。
- 不得讓前端傳入 consultantId 後直接查詢該顧問資料；查詢身份須由後端可信任憑證決定。
- 不得在資料源、認列月份、規則版本、人工覆核或 fingerprint 不清楚時重跑正式 Generate。
- 不得把姓名、手機、LINE UID 或可變推薦碼當作永久主鍵。
- 不得直接覆寫已核准、已付款、已調整或已追回的歷史；更正必須追加可追溯紀錄。
