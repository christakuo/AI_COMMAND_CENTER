# Task 04G-2C：歷史測試資料標準化處理規劃

## 1. 任務目的

本任務用於規劃如何安全處理正式資料庫中的歷史測試資料，避免測試資料被誤認為正式成交、正式會員、正式顧問歸屬或顧問獎金候選資料，進而干擾付款資料維護、正式 Preview、資料驗證及後續獎金流程。

本階段只定義盤點與標準化方法，不建立待修正清單、不修改正式資料，也不執行任何獎金相關函式。

## 2. 已知背景

- Task 04G-2A 盤點發現 10 筆「是否已付款＝是，但付款完成時間空白」資料。
- Task 04G-2B 經使用者人工確認，這 10 筆皆為歷史測試資料。
- 測試來源包含健康評估、推薦碼、CRM 等流程測試。
- 這 10 筆不是正式成交名單。
- 這 10 筆不是顧問獎金對象。
- 不應補付款完成時間。
- 不應產生正式獎金草稿。
- 正式資料庫中的測試資料不只這 10 筆；這 10 筆只是本次付款欄位盤點抓出的第一批已知案例。
- 其他工作表或其他欄位也可能存在歷史測試資料，各表數量尚未完整盤點。

因此，不能將這 10 筆視為全部測試資料，也不能只清理 leads 後就認定正式資料庫已完成標準化。

## 3. 歷史測試資料範圍定義

### 可能存在的工作表

| 工作表／資料表 | 可能存在的測試資料 | 主要風險 |
|---|---|---|
| `leads_潛在會員名單` | 測試會員、測試付款狀態、測試顧問歸屬、測試手機 | 被誤認為正式成交或獎金候選名單 |
| `referral_events_推薦事件紀錄` | 測試推薦碼、測試事件、測試 LINE 使用者、內部測試顧問 | 影響推薦來源與顧問保護判斷 |
| `health_assessments_健康評估紀錄` | 測試健康評估 ID、測試 submissionId、測試會員資料 | 被誤認為正式健康評估或產生正式 CRM 關聯 |
| `consultants_顧問主檔` | 內部測試顧問、測試推薦碼、測試帳號 | 被誤認為正式顧問或獎金歸屬對象 |
| `bonus_records_獎金明細表` | 目前正式尚未建立；未來若建立，可能混入測試獎金草稿 | 污染正式獎金審核、結算及付款紀錄 |
| 其他後續新增正式資料表 | 測試會員、事件、訂單、付款、顧問或批次資料 | 測試資料跨表擴散，影響正式報表與流程 |

### 可能的辨識特徵

測試資料不一定只有在「是否測試資料＝是」時才算測試資料。歷史資料可能以以下方式出現：

- `TEST_LINE`。
- `TEST_CRM`。
- 內部測試顧問。
- 顧問 ID `HC9001`。
- 測試會員或測試姓名。
- 測試手機號碼。
- 測試 submissionId。
- 測試推薦碼。
- 測試健康評估 ID。
- 測試事件 ID 或備註。
- 測試流程留下的付款、成交或 CRM 階段狀態。
- 已知測試日期、測試批次或測試操作人員紀錄。

必須採取「先盤點、再判定、再處理」的順序，不可只依單一欄位、名稱關鍵字或特定顧問 ID 直接批次判定全部資料。

## 4. 歷史測試資料建議標準

| 欄位／項目 | 建議標準 | 本階段處理 |
|---|---|---|
| 是否測試資料 | 經人工確認為測試資料後，建議標示為「是」 | 不直接修改 |
| 是否已付款 | 若只是測試流程留下的付款狀態，建議另行評估改為「否」或增加歷史測試註記 | 不直接修改 |
| 付款完成時間 | 不補造正式付款時間 | 維持原狀 |
| 歸屬顧問 ID | 若為 `HC0000` 或內部測試顧問，保留歷史值並註明不發獎金 | 不直接修改 |
| 歸屬顧問姓名 | 官方或內部測試顧問名稱應保留歷史紀錄 | 不直接修改 |
| 歸屬爭議狀態 | 測試資料不應維持「待審核」；可另行規劃測試資料註記 | 不直接修改 |
| 備註／後續標示 | 建議記錄「歷史測試資料，不列入正式獎金」 | 後續任務決定欄位與寫法 |
| 沒有「是否測試資料」欄位的工作表 | 先盤點現有欄位與跨表關聯，再決定新增欄位、備註或外部清單策略 | 不直接新增欄位 |

### 標準化注意事項

- 不把測試付款狀態補成正式成交事實。
- 不因欄位空白就推測付款時間、顧問歸屬或推薦來源。
- 保留原始 ID、歷史顧問與流程紀錄，以維持追溯能力。
- 若需要改寫欄位，必須記錄修改前值、修改後值、原因、日期及人員。
- 其他工作表若沒有「是否測試資料」欄位，應先規劃欄位策略，不可直接新增或批次修改。

## 5. 處理原則

1. 不直接刪除歷史測試資料。
2. 不直接批次改寫正式 Sheet。
3. 不把測試資料補成正式成交資料。
4. 不補付款完成時間。
5. 不因測試資料產生 `bonus_records`。
6. 不執行 `generateConsultantBonusDrafts()`。
7. 先建立待修正清單，再人工確認，再小批次處理。
8. 每次處理正式資料前，都需建立最新正式 Sheet 備份。
9. 不同工作表分開盤點，不能將 leads 的判定規則直接套用全部工作表。
10. 測試資料標準化優先採取「標記與排除」，不是刪除資料。
11. 每批修改後保留修改紀錄，並進行人工抽查或逐筆核對。
12. 未確認的資料留在待確認清單，不可自行推測為測試或正式資料。

## 6. 建議待修正清單欄位

未來 Task 04G-2D 可建立一份獨立、唯讀盤點用的跨工作表待修正清單，建議包含：

| 欄位名稱 | 用途 |
|---|---|
| 工作表名稱 | 識別資料來源工作表 |
| 資料列號 | 回查工作副本或正式 Sheet 的位置 |
| 主要 ID | 名單 ID、事件 ID、健康評估 ID、顧問 ID 等 |
| LINE 使用者 ID | 核對跨表身分與測試帳號 |
| 顧問 ID | 核對顧問歸屬或測試顧問 |
| 顧問姓名 | 與顧問 ID 交叉核對 |
| 目前是否已付款 | 保留盤點當下值 |
| 目前付款完成時間 | 保留盤點當下值 |
| 目前是否測試資料 | 保留盤點當下值 |
| 測試資料判定依據 | 記錄 TEST 標記、測試帳號、人工確認或流程來源 |
| 人工判定 | 測試資料、正式資料、待確認 |
| 建議處理 | 標示測試、調整狀態、保留原值、補備註等 |
| 是否已確認 | 控制是否可進入修改階段 |
| 是否已修正 | 記錄正式資料是否完成處理 |
| 修正日期 | 留存正式修改日期時間 |
| 修正人員 | 留存執行及負責人員 |
| 備註 | 記錄來源、風險、跨表關聯及例外情況 |

待修正清單本身不應自動修改正式資料，也不應直接作為獎金資格依據。

## 7. 10 筆已知 leads 資料的建議分類方向

以下 10 筆只是第一批已知案例，不代表正式資料庫中的全部測試資料：

| 名單 ID | 已知情況 | 建議處理方向 |
|---|---|---|
| `LD0001`、`LD0002`、`LD0003` | 資料不完整；使用者確認為歷史測試資料 | 列入歷史測試資料待標準化清單，不補付款時間 |
| `LD000004`、`LD000005`、`LD000006`、`LD000008` | `HC0000` 官方來源；使用者確認為歷史測試資料 | 列入待標準化清單，保留官方歸屬歷史，不發推薦獎金 |
| `LD000007` | 已標示「是否測試資料＝是」 | 維持測試資料排除，不進入正式獎金流程 |
| `LD000009`、`LD000010` | 內部測試顧問 `HC9001`；使用者確認為歷史測試資料 | 列入待標準化清單，保留測試顧問歷史，不發獎金 |

上述分類只記錄目前已知人工判定。正式修改前仍須在待修正清單中逐筆核對資料列、跨表關聯及原始值。

## 8. 對顧問獎金流程的影響

- 這 10 筆不應計入 `plannedCreateCount`。
- 其他尚未盤點到的測試資料也不得進入顧問獎金流程。
- 不應因歷史測試資料建立正式獎金草稿。
- 重新 Preview 前若尚未標準化，這 10 筆仍應被現有資格規則排除。
- 未來若統一標示為「是否測試資料＝是」，Preview 的 `TEST_DATA` 排除數可能增加，屬於可預期變化。
- `plannedCreateCount` 應維持 `0`，直到出現真正正式付款完成、顧問歸屬有效且非測試資料的名單。
- 在跨工作表測試資料盤點及必要人工確認完成前，不執行正式 Generate。

### Task 04G-2F：正式 Sheet 小批次資料標準化

- 只有本階段才可能修改正式 Sheet。
- 每次修改前建立最新備份。
- 每次只處理小批資料，保留修改前後值及人員紀錄。
- 不直接執行正式獎金草稿產生。

### Task 04G-2G：標準化後重新正式 Preview

- 標準化完成後重新執行唯讀 Preview。
- 人工比對 `excludedSummary`、`TEST_DATA` 與 `plannedCreateCount`。
- Preview 不一致時立即停止，不執行 Generate。

Task 04G-2C 只完成規劃；Task 04G-2D 才整理跨工作表清單；Task 04G-2F 才可能修改正式 Sheet。每次修改正式 Sheet 前都必須備份，正式 Generate 仍未執行。
