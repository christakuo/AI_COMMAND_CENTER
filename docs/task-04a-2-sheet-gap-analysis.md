## 3. 各分頁支援度矩陣

### 3.1 `consultants_顧問主檔`

| 分析項目 | 現有證據 | 支援度與處理建議 |
|---|---|---|
| 顧問身分與狀態 | 顧問ID、目前位階、顧問狀態、合約狀態、啟用／停權／終止日期 | 可沿用為顧問主檔基礎；須定義哪一組狀態決定合作有效性 |
| 上下級關係 | 推薦人ID、上層導師ID、組織路徑、組織層級 | 部分支援；屬「目前狀態」，不能取代成交當下組織快照 |
| 導師資格 | 是否具導師資格、導師資格狀態、開始／暫停／失效日 | 可沿用基礎欄位；缺晉升申請、人工核准及完整資格事件歷史 |
| 季度維護 | 最近考核季度、本季直推會員數、連續未達標季數 | 僅摘要；不足以重建每季 3 名、過渡季、連續兩季喪失及 5 名恢復的判定證據 |
| 可領獎資格 | `是否可領獎金`、各類 `是否可領…` 與 `可領…` 欄位並存 | 語意重複且可能衝突；應建立單一資格判定來源，其他欄位僅作衍生摘要或淘汰 |
| 培育期間 | 培育來源導師ID、開始日、到期日、狀態 | 部分支援；需保存分支獨立事件、適用組織範圍及資格暫停期間不成立的證據 |
| 權限失效 | 停權／終止及導師暫停／失效日期 | 有時間依據；缺權限撤銷事件、實際生效時間及稽核結果 |

目前位階、顧問狀態、導師資格狀態等制度型下拉已存在。`直推會員成交件數`、`團隊會員成交件數`、`本季直推會員數`及各種可領獎旗標不應作為正式獎金計算主來源；它們是可被重算的摘要，正式計算須回到有效成交、資格事件及組織快照。

### 3.2 `leads_潛在會員名單`

| 分析項目 | 現有證據 | 支援度與處理建議 |
|---|---|---|
| 推薦與歸屬 | 推薦碼、歸屬顧問ID、推薦保護起訖、是否保護期內、歸屬爭議狀態 | 可作 CRM 與推薦歸屬的來源證據；正式獎金仍須保存最終歸屬判定快照 |
| 轉換關聯 | 轉換會員ID、轉換訂單ID、轉換方案ID | 可銜接正式訂單；須定義一個 lead 對多次訂單或既有會員的關係 |
| 成交／付款摘要 | 是否已簽會員合約、是否已付款、成交日期、成交金額、CRM 階段 | 僅 CRM 摘要，不得作財務唯一依據 |
| 獎金摘要 | 是否列入顧問獎金、獎金歸屬顧問ID | 可供 CRM 顯示或人工提示；不得取代訂單、入帳、規則版本及正式獎金明細 |
| 重複及爭議 | 是否重複資料、合併至名單ID、歸屬爭議狀態 | 有基礎；正式計獎前仍需可稽核的合併、改派及人工決議事件 |

lead 轉為訂單後，付款、入帳、退款、方案版本、件數及獎金成立應由正式交易與獎金資料負責；lead 保留推薦來源及 CRM 歷程，不應被反向更新成財務主帳。

### 3.3 `plans_方案規則表`

| 分析項目 | 現有證據 | 支援度與處理建議 |
|---|---|---|
| 基本方案 | 方案ID、名稱、類型、卡別、人數基準、方案金額、推廣獎金、件數換算 | 可沿用基礎資料 |
| 目前方案值 | 下拉只見個人、家庭 3 人、企業 10 人三種基本方案及三個方案ID | 不足以單靠固定列支援家庭 4／5 人、企業 10 人以上及未來擴充 |
| 動態公式 | 有人數基準、獎金換算說明、客製方案金額 | 未見可機器執行且可版本化的金額、基本獎金及件數公式 |
| 0.5 件 | 有件數換算欄 | 欄位形式可能可存小數，但診斷無法證明格式、精度、驗證及計算全程支援 0.5 |
| 版本與生效 | 生效日、結束日、方案版本、是否目前版本、前一版方案ID | 有版本骨架；缺核准狀態、修改原因及已被訂單引用後不可覆蓋的控制 |
| 件數用途 | 是否列入個人／團隊／晉升／活動／組織獎件數 | 可沿用為適用旗標；仍需和封版規格統一件數來源與公式版本 |

Task 04A-1 要求的家庭 3 至 5 人與企業 10 人以上是動態人數公式。三筆基本方案可作方案族群起點，但不足以證明每一合法人數、公式版本及成交快照都能被正確保存。後續資料模型須決定「方案族群＋版本化公式」或「各人數版本列」等表達方式，但本文件不選定方案。

### 3.4 `orders_訂單主檔`

| 分析項目 | 現有證據 | 支援度與處理建議 |
|---|---|---|
| 方案與金額 | 方案ID／名稱／類型、標準／客製／實際金額、推廣獎金、件數換算 | 可作成交摘要；缺實際方案人數、方案規則版本及不可變計算快照 |

| 組織歸屬 | 推廣顧問、上層導師、培育來源導師 | 不足；缺最近有效導師、完整組織路徑、各資格生效時間及多層不重複判定快照 |

`推廣獎金`、`件數換算`、`是否已產生獎金明細`、`追回獎金金額`及撥款狀態均不應成為唯一正式依據。訂單應保存成交事實與快照；每一獎項、調整及追回應由正式獎金明細與稽核事件負責。

## 4. 欄位及狀態落差

| 封版規格要求 | 現有可見結構 | 關鍵落差 |
|---|---|---|
| 家庭 3 至 5 人、企業 10 人以上動態公式 | plans 有三筆基本方案、金額／獎金／件數欄 | 缺可執行、可版本化的動態人數公式及成交引用版本 |

| 90 天保護快照 | leads 有保護欄；orders 無完整欄 | 缺成交時最終判定、依據及人工改派快照 |
| 最近有效導師與組織快照 | consultants／orders 有現況型導師欄 | 缺完整路徑、資格生效點及不可變成交快照 |
| 導師晉升與維護 | consultants 有狀態及摘要 | 缺每季事件、過渡季、5 名恢復申請與核准歷史 |
| 培育獎一年 | consultants 有起訖及狀態 | 缺分支範圍、資格暫停不成立及每案適用快照 |
| 規則版本不可變 | plans／campaigns 有版本欄 | orders／bonus_records 未見完整引用；缺核准後鎖定 |
| 正常獎金狀態 | bonus_records 有舊狀態值 | 用詞與語意需遷移，且不得跳過人工審核 |
| 取消與追回 | orders／bonus_records 有摘要欄 | 缺負項明細、部分追回、原獎金及原訂單關聯 |
| 防止重複計獎 | orders 有產生旗標 | 缺正式唯一鍵、重跑策略及批次鎖定 |
| 週結／月結不可變快照 | 有結算月份／批次文字欄 | 缺獨立批次生命週期、納入明細及不可覆蓋快照 |
| 完整人工調整與稽核 | 有建立／更新及審核欄 | 缺事件式前後值、原因、角色、操作者、覆核者及時間 |

## 6. 必須保留／修改／新增的資料能力

### 6.1 可保留的能力

- 六個分頁的穩定識別欄位、建立／更新稽核欄及基本版本鏈概念。
- plans 的方案分類、金額／獎金／件數及各用途納入旗標。
- orders 的訂單、lead／會員關聯、入帳日、退款摘要及顧問角色欄。
- bonus_records 的一獎項一明細、金額拆分、受益人及來源關聯骨架。
- bonus_campaigns 的活動ID、規則ID、期間、週期、門檻、擇優及版本骨架。

### 6.2 必須修改或重新定義

- 顧問資格旗標的主從關係，避免同義欄位互相矛盾。
- lead 與 orders 的成交／付款責任邊界。
- plans 如何表達動態人數公式、0.5 件及版本生效。
- bonus_records 的正常與例外狀態、狀態轉換及追回語意。
- 訂單、獎金與活動的規則版本引用和不可變控制。
- 所有摘要欄位須明確標示為衍生值，不得取代交易或稽核事實。

### 6.3 需要另行設計的資料能力

以下能力在現有六張分頁中不足，Task 04A-3 應設計其資料關係；本文件不指定最終分頁名稱：

1. 多會員／訂單成員關聯：保存家庭與企業每一成員、實際人數及成員狀態。
2. 分次付款明細：保存應收、每筆收款、累計實收、未收餘額、入帳確認及退款關聯。
3. 不可變成交與計算快照：保存方案、歸屬、90 天保護、資格、組織路徑及規則版本。
4. 結算批次：區分週結、月結、審核、核准、排款及實際發放，保存納入明細快照。
5. 人工調整與稽核事件：保存前後值、原因、佐證、角色、操作者、覆核者及時間。
6. 負項調整與追回關聯：連結原獎金、原訂單、退款、新方案、取消、部分追回及已追回。
7. 防重與重算控制：提供唯一防重鍵、重算版本、批次鎖定及失敗重跑策略。
8. 資格與組織歷史：保存晉升、季度考核、暫停、喪失、恢復、分支獨立及權限撤銷事件。

## 7. 個資、權限及稽核風險

1. 現有分頁同時存放姓名、手機、Email、LINE UID、身分證、地址、健康摘要、金融資訊及獎金資料。獎金計算與顧問大廳 API 必須採欄位白名單，不可直接回傳整列。
2. 一般顧問只可看本人獎金及本人推薦會員的遮罩姓名、遮罩手機、方案、人數、件數、入帳日及狀態。
3. 有效導師只可看現行管理團隊的必要資料；不可看完整會員個資、健康資料、銀行資料或與組織獎無關的下層完整收入。
4. 分支獨立後的原導師在培育期間只可看案件編號、件數及培育獎；導師暫停或喪失時應立即撤銷團隊會員資料權限。
5. `bonus_records` 含撥款帳戶後五碼，前端及非財務 API 預設不得取得；財務查詢也須記錄用途與操作者。
6. 顧問主檔的目前資格與組織關係可能日後改變，若不保存成交快照，會造成錯誤改派與越權查詢。
7. 現有建立／更新欄不足以證明每次審核、調整、核准、撥款及追回；必須保存不可覆蓋的事件紀錄。
8. 正式顧問大廳必須使用可信任的 LINE 身分驗證，不得信任前端自行傳入的使用者識別或測試 fallback。

## 8. Task 04A-3 資料模型建議範圍

Task 04A-3 應先完成規格設計，不應直接啟用計算或撥款。建議範圍如下：

1. 定義資料權責圖：CRM、顧問資格、方案、訂單、付款、歸屬、獎金、活動、結算及稽核的主來源。
2. 定義核心識別與關聯：lead、會員、訂單、訂單成員、付款、顧問、資格事件、組織快照、規則版本、獎金及批次。
3. 定義版本化模型：方案公式、一般獎金規則、活動期別及規則的生效、核准、停用與歷史鎖定。
4. 定義成交快照：完整人數、全額入帳、90 天保護、最終顧問、最近有效導師及完整組織路徑。
5. 定義獎金狀態機：正常流程、暫停／爭議、取消、調整、追回及禁止跳過人工審核的轉換條件。
6. 定義防重與重算：唯一鍵、試算版本、批次重跑、退款回溯及負項關聯。
7. 定義週結／月結與撥款：不可變批次快照、管理者核准及財務確認的分工。
8. 定義權限與稽核：角色可視欄位、遮罩、即時停權、敏感查詢及管理操作事件。
9. 產出現有欄位的保留、改名、衍生、遷移與停用對照；尚不直接變更正式 Sheet。

完成資料模型及遷移規格後，再進入基本推廣獎金的純計算與 dry-run；不得由本分析直接啟用自動計獎。

## 10. 結論及正式實作前阻塞

六個正式分頁已具備顧問、CRM、方案、訂單、獎金及活動的結構骨架，可進入 Task 04A-3 資料模型設計；但目前尚不具備安全啟用正式自動計獎或撥款的條件。

正式實作前至少須排除或完成：

1. HC9001 的 90 天推薦保護正式 Web App 寫入異常；在修正並驗證前，推薦歸屬及其衍生的基本、導師、活動與組織獎均不可自動成立。
2. 動態方案公式、分次付款、多會員、成交三要件及最終歸屬的正式資料模型。
3. 方案、一般獎金、活動及組織規則的版本引用與不可變快照。
4. 獎金狀態遷移、人工審核、負項追回、唯一防重及結算批次設計。
5. 顧問與導師權限、正式 LINE 身分驗證、遮罩及完整稽核事件。
6. 正式生效日、退款法律文字及財務責任等營運／法律決策。

因此，下一個最小任務應是 Task 04A-3A：先定義資料來源權責、核心實體關係、不可變快照及版本策略；完成審核後，再設計狀態機、結算批次及欄位遷移。任何階段均不應直接開啟自動核准或自動撥款。
