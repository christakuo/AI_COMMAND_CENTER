# Task 04F：成交／付款完成資料維護 SOP

## 1. SOP 目的

本 SOP 用於維護正式 `leads_潛在會員名單` 的成交與付款資料，使付款事實、顧問歸屬及 CRM 狀態一致，讓顧問獎金系統可以安全判斷是否應規劃產生待審核獎金草稿。

本 SOP 提供非工程背景人員可直接照做的人工操作流程。資料維護完成不代表獎金已成立、已核准或已付款。

## 2. 正式成交定義

1. 正式成交等於「付款完成」。
2. 已簽會員合約但尚未付款，不算正式成交。
3. CRM 階段為「已成交」或「付款完成」，只能作為交叉檢查，不可單獨作為發放獎金的依據。
4. 「是否已付款」為「是」時，必須同時填寫「付款完成時間」。
5. 沒有付款完成時間的名單，不得進入正式獎金草稿。
6. 付款已取消、退款或刷退時，不得視為付款完成。

### 判斷原則

| 判斷順序 | 應確認事項 | 是否足以認定正式成交 |
|---:|---|---|
| 1 | 已確認實際款項入帳且未取消、退款或刷退 | 是，繼續核對其他必要欄位 |
| 2 | 「是否已付款」為「是」且有付款完成時間 | 是，繼續核對顧問歸屬與資料資格 |
| 3 | 只有簽約紀錄 | 否 |
| 4 | 只有 CRM 階段為已成交／付款完成 | 否 |
| 5 | 只有 CRM 階段更新時間 | 否 |

## 3. `leads_潛在會員名單` 欄位維護規則

### 維護角色說明

- 「財務／收款確認人員」：可查證實際收款、退款、刷退及付款取消狀態的人員。
- 「CRM 管理人員」：負責依已確認事實更新正式 Sheet 的指定人員。
- 「顧問管理負責人」：可確認推薦碼、顧問歸屬及爭議處理結果的人員。
- 同一人兼任多個角色時，仍須按照本 SOP 完成每一項核對，不可略過。

| 欄位名稱 | 誰維護 | 什麼時候填 | 可接受值／格式 | 錯誤填寫風險 |
|---|---|---|---|---|
| 名單 ID | CRM 管理人員／系統既有資料 | 建立名單時；付款維護時只核對 | 不可空白；每筆唯一，例如 `LD000001` | 空白會被排除；重複會造成名單與獎金歸屬混亂 |
| 潛在會員姓名 | CRM 管理人員 | 建立名單或確認身分時 | 與會員正式資料一致 | 找錯名單或將付款記到他人名下 |
| 手機號碼 | CRM 管理人員 | 建立名單或會員更新聯絡方式時 | 完整且可核對的正式手機格式 | 同名會員辨識錯誤、付款資料錯配；獎金資料只可寫入遮罩號碼 |
| 推薦碼 | 顧問管理負責人／CRM 管理人員 | 確認推薦來源時 | 有效推薦碼，例如 `HC9999`；不得臆測補填 | 推薦來源錯誤，導致顧問獎金歸屬錯誤 |
| 歸屬顧問 ID | 顧問管理負責人 | 顧問歸屬確認後；付款前再次核對 | 有效顧問 ID；不可空白；不得為官方帳號 `HC0000` 才可能列入獎金 | 空白或 `HC0000` 會被排除；填錯會造成獎金誤歸屬 |
| 歸屬顧問姓名 | 顧問管理負責人／CRM 管理人員 | 顧問 ID 確認後 | 必須與顧問 ID 對應 | 顧問 ID 與姓名不一致，人工審核容易誤判 |
| 是否已付款 | 財務確認後由 CRM 管理人員更新 | 實際收款完成且確認未取消、退款或刷退後 | `是`／`否`；不得用其他近似文字 | 誤填「是」可能讓名單進入獎金候選；漏填則會被排除 |
| 付款完成時間 | 財務確認後由 CRM 管理人員更新 | 與「是否已付款＝是」同一次操作填寫 | `yyyy-MM-dd HH:mm:ss`，例如 `2026-07-02 14:00:00` | 空白或格式錯誤會被排除；填入簽約時間會造成獎金資格誤判 |
| CRM 階段 | CRM 管理人員 | 業務狀態確實改變時 | 依正式用語填「付款完成」或「已成交（付款完成）」 | 只改階段但未實際付款，可能讓人工誤認已成交 |
| CRM 階段更新時間 | CRM 管理人員／系統 | CRM 階段更新時 | 正式日期時間格式；只代表階段更新時間 | 被誤當付款完成時間，造成錯誤成交日期 |
| 是否測試資料 | CRM 管理人員／測試負責人 | 建立測試名單時即標示 | `是`／`否` | 測試資料未標「是」可能混入正式獎金候選 |
| 爭議狀態 | 顧問管理負責人 | 發現顧問歸屬、推薦來源或付款爭議時 | 依正式選項；未解決時至少標示「待審核」 | 爭議名單可能被誤認為可發獎金 |
| 保護到期日 | 顧問管理負責人／CRM 管理人員 | 推薦保護建立或調整時 | 正式日期格式，依推薦保護規則填寫 | 顧問歸屬及推薦保護判斷錯誤，引發獎金爭議 |

## 4. 付款完成資料填寫 SOP

### 操作前原則

- 必須由可確認收款事實的人員提供依據，再由指定人員更新正式 Sheet。
- 不確定、資料不一致或有爭議時，立即停止，不要自行推測補值。

### 人工操作順序

1. 確認實際收款已完成。
2. 確認該筆款項不是退款、刷退或付款取消。
3. 在正式 `leads_潛在會員名單` 找到對應的名單 ID。
4. 以會員姓名與手機號碼交叉確認是同一位會員。
5. 確認歸屬顧問 ID 與顧問姓名互相對應。
6. 確認歸屬顧問不是官方帳號 `HC0000`。
7. 將「是否已付款」改為「是」。
8. 同一次操作填入「付款完成時間」，格式必須為 `yyyy-MM-dd HH:mm:ss`。
9. 依目前正式用語，將 CRM 階段更新為「付款完成」或「已成交（付款完成）」。
10. 不要把「CRM 階段更新時間」當作「付款完成時間」。
11. 不要把「簽約時間」當作「付款完成時間」。
12. 若顧問歸屬、推薦碼、保護期或付款狀態有爭議，先標示爭議並停止，不要把名單改成可發獎金狀態。
13. 完成後重新讀一次同列資料，確認名單 ID、會員、顧問、付款狀態與付款時間均正確。

### 退款、刷退或付款取消處理

若原先已標示付款完成，後續發生退款、刷退或付款取消：

1. 立即通知財務、CRM 管理人員及顧問管理負責人。
2. 在未定義正式沖銷流程前，不得自行刪除歷史或以空白掩蓋事實。
3. 將該筆資料標示為爭議／停止處理，禁止進入後續獎金流程。
4. 另開任務確認付款狀態、更正紀錄及既有獎金草稿是否需要撤銷或調整。

## 5. 不應產生獎金草稿的情況

以下任一情況成立時，都不得產生正式獎金草稿：

- 「是否已付款」不是「是」。
- 「付款完成時間」空白。
- 歸屬顧問 ID 空白。
- 歸屬顧問 ID 為官方帳號 `HC0000`。
- 「是否測試資料」為「是」。
- 名單 ID 空白。
- 付款已取消、退款或刷退。
- 顧問歸屬爭議尚未處理完成。
- 會員只是簽約但尚未付款。
- CRM 階段已更新，但實際尚未付款。
- 名單 ID 重複或會員資料無法確認。
- 顧問 ID 與顧問姓名不一致。

## 6. 正式 Preview 前人工核對清單

執行 `BonusService.gs`／`logPreviewConsultantBonusDrafts()` 前，操作人員必須逐項勾選：

### Sheet 與付款資料

- [ ] 正式 Google Sheet 已建立最新副本備份。
- [ ] 所有「是否已付款＝是」的名單都有付款完成時間。
- [ ] 付款完成時間格式均為 `yyyy-MM-dd HH:mm:ss`。
- [ ] 付款完成時間是實際收款完成時間，不是簽約時間或 CRM 階段更新時間。
- [ ] 沒有付款取消、退款或刷退資料被列為可發獎金。

### 名單與顧問資料

- [ ] 歸屬顧問 ID 不是空白。
- [ ] 歸屬顧問 ID 不是 `HC0000`。
- [ ] 顧問 ID 與顧問姓名一致。
- [ ] 「是否測試資料」不是「是」。
- [ ] 名單 ID 不空白。
- [ ] 名單 ID 沒有重複。
- [ ] 爭議狀態不是「待審核」或其他未完成狀態。

### Preview 結果

- [ ] `plannedCreateCount` 等於人工核對出的可發獎金筆數。
- [ ] `errorCount` 必須為 `0`。
- [ ] 若 `excludedSummary` 出現 `MISSING_PAYMENT_COMPLETED_AT`，先補正付款完成時間或確認該筆不應進入獎金流程。
- [ ] 若 `excludedSummary` 出現 `MISSING_CONSULTANT_ID`，先完成顧問歸屬確認。
- [ ] 若 `excludedSummary` 出現 `OFFICIAL_CONSULTANT_HC0000`，確認該筆維持官方歸屬且不得產生顧問獎金。
- [ ] 上述異常未處理完畢前，不進入下一步。

## 7. 付款完成資料範例

### 可發獎金資料範例

| 欄位 | 範例值 |
|---|---|
| 是否已付款 | 是 |
| 付款完成時間 | `2026-07-02 14:00:00` |
| 歸屬顧問 ID | `HC9999` |
| 是否測試資料 | 否 |

此範例仍須同時通過名單 ID、顧問歸屬、爭議狀態、防重及其他正式資格核對，才可列入 Preview 的預計建立清單。

### 不可發獎金資料範例

| 情況 | 不可發獎金原因 |
|---|---|
| 是否已付款為「是」，但付款完成時間空白 | 缺少實際付款完成時間 |
| 是否已付款為「否」，但 CRM 階段填寫付款完成 | CRM 階段不可取代付款事實 |
| 歸屬顧問 ID 為 `HC0000` | 官方帳號不得產生顧問推薦獎金 |
| 是否測試資料為「是」 | 測試資料不得進入正式獎金流程 |
| 已簽約但尚未付款 | 尚未達成正式成交定義 |

## 8. 後續銜接顧問獎金流程

1. 完成付款資料維護與人工核對後，才可執行正式 Preview。
2. 正式 Preview 只執行 `BonusService.gs`／`logPreviewConsultantBonusDrafts()`。
3. Preview 成功，且 `plannedCreateCount` 與人工核對筆數完全一致後，才可另開任務規劃建立 `bonus_records_獎金明細表`。
4. `ensureBonusRecordsSheet()` 必須單獨執行，執行後人工核對 19 欄 Header。
5. `generateConsultantBonusDrafts()` 必須另開任務，不可在本 SOP 的資料維護階段直接執行。
6. 首批正式獎金草稿產生後，初始狀態為「待審核」，不是「已付款」。
7. 若 Preview 的 `errorCount` 不為 `0`、筆數不一致或出現未處理排除原因，立即停止並另行處理。

## 9. 安全限制

- 本 SOP 不會產生任何獎金或獎金草稿。
- 本 SOP 不會部署 Apps Script。
- 本 SOP 不會執行 `generateConsultantBonusDrafts()`。
- 本 SOP 不會執行 `ensureBonusRecordsSheet()`。
- 本 SOP 不會建立 `bonus_records_獎金明細表`。
- 本 SOP 只規範正式 `leads_潛在會員名單` 的人工資料維護與核對流程。
- 本次文件任務不修改 Apps Script repo、LIFF repo 或正式 Google Sheet。
